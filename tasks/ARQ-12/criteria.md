# ARQ-12 — Acceptance criteria

## Need
Projects generated by java-skeleton must separate three kinds of tests: unit (`test`), integration
(`intTest`) and architecture (`archTest`). Each must be runnable on its own and all must be part of
the build's `check`. The integration tests of `spring-gradle` must be able to simulate external HTTP
services with WireMock. The architecture tests must validate the pirca layer convention (ARQ-25)
through one general `archTest` in the 3 templates, explicitly disabling the layers a template does
not have. Adding this must not change the `main` dependencies of any template.

## Scope
Repository `java-skeleton`, templates `spring-gradle`, `java-app` and `java-library`: Gradle
configuration (`gradle/*.gradle`, `gradle/libs.versions.toml`, `gradle.properties`), sample tests,
a sample `HelloService` in `spring-gradle`, and the generated READMEs / repo docs that describe the
test suites.

## Acceptance criteria
Each criterion is checked on projects generated from each template and built with the generated
Gradle wrapper (Java 25, Spring Boot 4 for spring-gradle).

- AC-1: Every generated project defines three separate suites, `test`, `intTest` and `archTest`,
  each runnable alone (`./gradlew test`, `./gradlew intTest`, `./gradlew archTest`) and each
  executing at least one test in every template.
- AC-2: `./gradlew check` in every generated project runs `test`, `intTest` and `archTest`
  (all three appear as executed in the task output).
- AC-3: Tests live in separate source sets/directories (`src/test`, `src/intTest`, `src/archTest`).
- AC-4: In `spring-gradle`, `intTest` includes a working sample integration test that stubs an
  external HTTP service with WireMock and passes. WireMock is not available to `java-app` or
  `java-library`.
- AC-5: The `archTest` suite is general: the same layer rules apply in the 3 templates and cover
  `controller → service → repository | client`, class-name suffixes `Controller` / `Service` /
  `Repository` / `Client` (package always `service`, never `business`), and a "no package cycles"
  rule applied in all templates.
- AC-6: Each layer rule carries the JUnit Platform tag `layer-<layer>` (`layer-controller`,
  `layer-service`, `layer-repository`, `layer-client`), verifiable by filtering the suite by tag.
  No specific annotation is required; the architect chooses the one that works for ArchUnit rules
  (for example `@ArchTag` on `@ArchTest` fields).
- AC-7: A layer is opted out only through `archTest.excludeLayers=<comma-separated layers>` in
  `gradle.properties`: `spring-gradle` → `repository,client`; `java-app` and `java-library` →
  `controller,service,repository,client` (only the cycles rule runs).
- AC-8: Layer rules never pass silently on an empty layer (`allowEmptyShould` is false). Control
  check: in `spring-gradle`, removing an exclusion for a layer with no classes (e.g. `repository`)
  makes `archTest` fail.
- AC-9: Control check: introducing a violation in a generated project (e.g. a controller calling a
  repository/client class directly, a misnamed class in a layer package, or a package cycle) makes
  `archTest` fail.
- AC-10: `spring-gradle` includes a sample `HelloService` (in package `service`) and `HelloController`
  delegates to it (`HelloController → HelloService`); the existing endpoint behavior is unchanged
  and the sample passes `archTest`.
- AC-11: The `main` dependencies of each template are unchanged: the resolved `compileClasspath`
  and `runtimeClasspath` of every generated project are identical before and after the change
  (compared against a baseline).
- AC-12: Every new library version (ArchUnit, WireMock, others needed) is declared in
  `gradle/libs.versions.toml`, resolves, and works with Java 25 and Spring Boot 4 (suites run
  green).
- AC-13: All three templates generate and build successfully (`./gradlew check`) end to end
  through java-skeleton's generator, and the `spring-gradle` app still starts and serves `/hello`.
- AC-14: The generated READMEs (and the repo README/DEVLOG where they describe the build) document
  the three suites and the `archTest.excludeLayers` opt-out, in English.
- AC-15: In `./gradlew check`, in every generated project, `test` executes before `intTest` and
  `archTest` (verifiable from the task execution order in the build output).

## Out of scope
- Quality tooling (step 4), JaCoCo, CI pipeline changes, hexagonal architecture.
- New layers or rules beyond ARQ-25.
- WireMock in `java-app` / `java-library`.
- Changes to `main` dependencies.

## Assumptions
- `intTest` and `archTest` follow the same Gradle structure in all 3 templates (separate source set
  per suite, wired into `check`); the exact mechanism is the architect's choice.
- `java-app` and `java-library` need at least one trivial test in `intTest` so the suite is not empty
  (an empty suite would not prove it runs).
- `archTest` is a general suite (same source in each template); only the exclusion list differs.
- "Layer names" for `excludeLayers` are `controller`, `service`, `repository`, `client`.
- Dependencies for the test suites (ArchUnit, WireMock) may be added to test configurations only.
